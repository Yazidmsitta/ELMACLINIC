# Phase 6 — payment foundation

Apply `202609110011_payment_recording.sql` after migrations 001–010. This increment implements payment recording in the backend; the Flutter payment form is connected through appointment details. Phase 5 live website verification is still outstanding.

Both active roles may POST `/api/v1/payments` with `appointment_id`, positive integer `amount_centimes`, `method` (CASH/CARD/TRANSFER) and a stable UUID `request_id`. The database assigns MAD currency, the authenticated recorder and current payment time. A retry of the same request by the same recorder returns the original payment ID. Reusing the key with different data or another recorder returns 409. Preserve the key while retrying an uncertain save; generate a new key only for a genuinely new payment.

Only confirmed, in-progress or completed unarchived appointments accept new payments. Partial payments are allowed; total collections may not exceed the appointment’s snapshotted service total. Shared booking locks and appointment row locks serialize concurrent collection and appointment changes. The payment and audit entry commit together. Staff cannot insert/update/delete payment rows directly. Cancelling an appointment does not delete its receipts or perform a refund; refund/adjustment commands require the later ledger workflow.

`GET /api/v1/appointments/{id}/balance` exposes only the appointment ID, MAD currency, service total, paid amount and remaining amount to either role. This operational balance supports collection; no clinic revenue, expenses, profit or other staff payment history is included. `GET /api/v1/payments` remains ADMIN-only with paginated ledger reads and RLS protection. Missing appointment IDs return 404, permission failures 403, malformed input 422, and duplicate-key/overpayment/status conflicts 409.

Automated tests cover partial collection, receipt replay, cross-recorder key collisions, USER ledger isolation, prohibited direct writes, invalid amounts/methods, overpayment, competing final payments and cancellation behavior. HTTP tests check USER recording versus ADMIN ledger access, privilege/currency overrides and failure status codes. PostgreSQL tests use PGlite and Auth/Storage fixtures; production multi-connection concurrency and live Supabase remain to be verified. No card processor, bank integration, refund, receipt printing or real money movement is performed.


Flutter payment form: open Paiements → Choisir un rendez-vous, then Encaisser un paiement on a confirmed, in-progress or completed appointment. The form shows the current appointment balance and supports Espèces, Carte and Virement. Amount parsing uses integer centimes and accepts a comma or period with up to two decimal places. A failed submission preserves its request ID and locks amount/method so retries cannot change an uncertain charge. To correct a rejected attempt, close and reopen after checking the refreshed balance; do not create a new payment blindly after a network failure. Success is shown only after the API returns the saved receipt ID.

The Figma payment source was re-inspected, retaining shared typography, warm fields, method selection and the olive confirmation button. The ADMIN ledger screen and daily/monthly summary cards are now implemented separately from the staff collection form. The new visual baseline is a Flutter test render, not Android device verification.


ADMIN ledger increment: apply migration `202609110012_payment_ledger.sql`. GET `/payments` now returns paginated enriched receipts with client name and snapshotted service labels, plus `today_centimes`, `month_centimes`, `clinic_date` and MAD currency. Daily and monthly boundaries use Africa/Casablanca and are computed independently to handle offset changes. Receipt history survives appointment/client archival; no fake pending/refunded entries are generated. Totals represent recorded gross collections, not profit or net revenue after refunds.

Flutter ADMIN Paiements displays these totals and receipts, with pull-to-refresh, pagination, empty/error states and refresh on returning to the tab. USER retains the collection entry and never constructs or requests the ledger. Both HTTP authorization and the database function reject USER access. Refunds, adjustment transactions, financial exports and method/date filters remain future work.
